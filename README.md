### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать/выключать отопление в своих домах.

**Мониторинг температуры:**

- Система получает данные о температуре с датчиков, установленных в домах.
- Пользователи могут просматривать текущую температуру в своих домах через веб-интерфейс

### 2. Анализ архитектуры монолитного приложения
- Язык программирования: Go (фреймворк [gin](https://github.com/gin-gonic/gin))
- База данных: PostgreSQL
- Архитектура: Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.
- Взаимодействие: Синхронное, запросы обрабатываются последовательно.
- Масштабируемость: Ограничена, так как монолит сложно масштабировать по частям.
- Развертывание: Требует остановки всего приложения.

### 3. Определение доменов и границы контекстов
#### Управление устройствами
- **Описание:** 
	- Управление умными устройствами, такими как датчики температуры, отопительные системы и другие устройства.
- **Пример функциональности:**
	- Добавление, удаление и обновление устройств.
- **Границы контекста:**
	- Взаимодействие с базой данных для хранения информации об устройствах.
	- API для управления устройствами.

#### Взаимодействие с устройствами
- **Описание:**
	- Сбор и отображение данных о температуре с датчиков.
- **Пример функциональности:**
	- Управление состоянием устройств (включение/выключение).
	- Мониторинг датчиков/состояния.
- **Границы контекста:**
	- Обновление данных в реальном времени.
	- Взаимодействие с конкретными устройствами.
	- API для взаимодействия с устройствами.

#### Устройства умного дома
- **Описание:**
	- Обеспечение взаимодействия умных устройств.
- **Пример функциональности:**
	- Просмотр текущей температуры.
	- Управление устройствами и отоплением.
- **Границы контекста:**
	- Взаимодействие с другими доменами через BFF.
	- Обработка запросов пользователей.

#### Пользовательский интерфейс
- **Описание:**
	- Обеспечение взаимодействия пользователей с системой через UI.
- **Пример функциональности:**
	- Просмотр текущей температуры.
	- Управление устройствами и отоплением.
- **Границы контекста:**
	- Взаимодействие с другими доменами через BFF.
	- Обработка запросов пользователей.

#### Аутентификация, авторизация
- **Описание:**
    - Управление пользователями, их регистрацией, входом в систему и проверкой прав доступа.
- **Пример функциональности:**
    - Регистрация новых пользователей.
    - Авторизация пользователей через логин и пароль.
    - Проверка прав доступа к ресурсам.
- **Границы контекста:**
    - Взаимодействие с базой данных для хранения данных пользователей.
    - API для регистрации, входа и проверки токенов.

### **4. Проблемы монолитного решения**

- Нет авторизации - пользователь А может запросить показания датчиков пользователя Б или управлять его отоплением.
- Проблемы масштабирования.
- Приходится платить специалисту, который вручную подключает новые дома к системе.
- Низкая отказоустойчивость.
- Высокая связанность компонентов.
- Сложно поддерживать кодовую базу.

# Задание 4. Создание и документирование API

### 1. Тип API

- В случае взаимодействия пользователя с системой будет использовать http взаимодействие, чтобы пользователь мгновенно получал реакцию системы на свои действия.
- В случае обмена телеметрией имеет смысл общаться асинхронно, т.к. нам не сильно важен результат записи телеметрии.
- В случае отправки пользователем команды - можно использовать http api для того, чтобы ответить пользователю об успешности отправки команды (она прошла валидацию и успешно сможет выполниться на устройстве), а дальше эта api уже создаст асинхронный пакет для доставки до устройства.
